> could not say), decided by the user on 2026-10-24 (`www.md` section 10 items 9 and 10). Prerendering is P1.
> Measured in Chromium (Playwright, `Pixel 7` profile, desktop Chromium, not a device) and in `cargo test`; numbers say which.

## 1. What a program can say

```
Header { Link { to: "#top" "cancho" }  Nav { label: "Sections" Link { to: "#try" "Try it" } } }
Main {
    Section {
        id: "try"
        Text { style: "eyebrow" "Try it" }
        Heading { level: 2 "Three ways in" }
        Article { Heading { level: 3 "See a refusal" } Text { "..." } }
        Details { summary: "Build instructions" Text { "..." } }
        Figure { Heading { level: 3 "A leak, a rule, a fix" } Text { "(the recording)" } Caption { id: "cap1" "One minute." } }
        Row { Link { to: "https://alpibru.com/manifesto" appearance: "primary" "Read the manifesto" } }
    }
}
Footer { Link { to: "agents.md" "agents.md" } }
```

| element | becomes | takes (beside `label:` on the containers) |
|---|---|---|
| `Heading` | `<h1>` to `<h4>` | `level:` (1 to 4, required), `id:`; its text is its name |
| `Section`, `Article`, `Figure`, `Header`, `Nav`, `Main`, `Footer`, `Aside` | `<section>`, `<article>`, `<figure>`, `<header>`, `<nav>`, `<main>`, `<footer>`, `<aside>` | `id:`; on `Section`, `Article`, `Aside` and `Figure` also `card: true` (section 12) |
| `Link` | `<a href>` | `to:` (a string literal, required), `appearance:` (`"primary"`, `"secondary"`, `"quiet"`, `"pill"`); its text is its name |
| `Details` | `<details>` with a `<summary>` first | `summary:` (required), `id:` |
| `Caption` | `<figcaption>` | `id:` |
| `Text { style: .. }` | `<p data-style="..">` (a `Text` without `style:` is still a `<span>`) | `style:` (`"eyebrow"`, `"lead"`, `"note"`, `"label"`, `"avatar"`) |

* **Accessibility keys come first, as everywhere in the language**: `Section { label: "Try it" id: "try" .. }`, not the other way round (a `label:` after a binding is a parse error).
* A heading, a link, a caption and a details are named by their text: `label:` and `role:` on them are `binding-unknown`. A landmark takes `label:` (an `aria-label`) and no `role:`.
* **`Link` text is written between the braces**, with `{n}` interpolation like a `Text`; a `Heading` and a `Caption` too. They are written as text directly inside the tag: `<h2>Step 0</h2>`, not a `<span>` in it
  (found by the first Chromium run: the text of a `Heading` was dropped until `holds_text` included the new elements).
* The names of the new elements are now the built-ins': a program that declares its own `component Link` and uses `Link { .. }` gets the primitive (a test), as `Table` did.
* Nothing here has behaviour of its own except the browser's: a `Details` opens and closes by itself (it is not program state), and a link goes where it goes. Replay has nothing to
  check beyond the lowering and the refusals; `examples/structure` replays its trace so that the handlers around the structure still run (4 steps, 9 checks).

## 2. The rules

Every refusal below has a rule tag in [`spec/diagnostics/README.md`](../spec/diagnostics/README.md), reached by a case of `tests/structure_corpus.json` (62 refusals).

| tag | refused |
|---|---|
| `heading-level-invalid` | no `level:`, or not an integer literal from 1 to 4 |
| `heading-level-skipped` | a level more than one deeper than the previous heading **of the same component's view**; an instance of another component resets the order (this view cannot see its headings) |
| `heading-empty` | no text, or only spaces |
| `id-invalid` | an `id:` that is not a letter then letters, digits, `-`, `_` (at most 64), or starts with `cui-` |
| `anchor-duplicate` | one `id:` on two elements of the program, or an `id:` inside a `For` |
| `anchor-unknown` | `Link { to: "#x" }` and no element has `id: "x"` |
| `link-scheme-refused` | `javascript:`, `data:`, `vbscript:`, `file:`, `ftp:`, any other scheme; `//host`; a space or control character; a user name before the host; no host; a `mailto:` with no `@`; an empty or bare `#`; a `#/route` (that is a `NavLink`) |
| `link-to-invalid` | no `to:`, or one that is not a string literal |
| `link-label-missing`, `link-label-generic` | no text; or "here", "click here", "click", "link", "this link", "this", "more", "read more", "learn more" |
| `link-appearance-invalid`, `text-style-invalid`, `details-incomplete` | a value outside its closed set; no or empty `summary:` |
| `card-invalid`, `grid-align-invalid` | a `card:` (of a `Section`, `Article`, `Aside`, `Figure` or `List`) that is not `true` or `false`; an `align:` of a `Grid` that is not `"stretch"` or `"center"` (section 12, *added 2026-10-29*) |
| `caption-misplaced` | a `Caption` that is not a direct child of a `Figure`, or a second one |
| `landmark-duplicate`, `nav-label-missing` | a second `Main`; with more than one `Nav`, one without `label:` |

**Corrections to `www.md` 5.2, measured in 5.2b and built here:** there is no `section-label-missing` (the page has 5 landmarks and 0 regions: an unnamed `Section` is not a landmark); a `Link` has no `rel`
(128 external links, 0 `target`); and `heading-level-skipped` would refuse the real page, whose first three cards are `h3`s under the `h1`.

**Not built in B1, and said so:** the skip link that a `Main` was to write and `sticky` (both built since, in [`page.md`](page.md)), `pressed:` (*built 2026-10-26 with an expression for its value, not a state field: [`www-port/gaps.md`](www-port/gaps.md) section 2*), `role: group` (*measured 2026-10-26: `Row { role: group label: ".." }` was already accepted; the switch needed `pressed:`, not this*), dynamic
links built from data (`link-to-invalid` says so), and `landmark-misplaced` (a `Main` inside an `Article` is not refused).

## 3. Authority and `diff`

* A `Link` is **not an effect**: `requires` is unchanged, the program needs no capability to put a link in a page, and `authority` in `diff` is unchanged (a test: adding two links gives `authority: unchanged`).
* The hosts a link names are listed because they are where a reader can be sent: `cancho-ui inspect effects <file> <Component>` has `"links": ["evil.example", "github.com", "mailto:example.org"]` (sorted, lower-cased,
  a port dropped, `mailto:` by its domain; absent when there are none), and `diff` prints `+ link evil.example` / `- link ..` as lines of their own, counts them in `change_count` (exit 5), and has a `links` delta in the JSON
  of a changed component (absent when equal, so no existing report changes). A relative link and a `#id` have no host and are not listed.
* A user name before the host (`https://bank.example@evil.example/`) is `link-scheme-refused`, so the host that is listed is the host a browser goes to.

## 4. The DOM, and why the recipe is in the IR crate

The tag, the attributes and the class of each element come from `cancho_ui_ir::structure` (`tag`, `attrs`, `class`, `summary`), which the JavaScript emitter reads. The prerenderer ([`www.md`](www.md) 5.2c,
P1) will read the same functions, so the two renderers cannot disagree about what a `Link` is. `tests/structure_corpus.json` holds, beside the refusals, **8 views and the DOM each must become**, serialised the way
the page serialises it (tags lower case, attributes sorted, double quotes, no whitespace between tags); `scripts/check-structure.js` builds each, loads it in Chromium and compares: 8 of 8 equal. The prerenderer must pass
the same 8.

The baseline stylesheet gives them a look and no more (`crates/cancho-ui/src/pwa.rs`): a link in a `header`, a `nav` or a `footer` is an inline-flex target at least 44 px high; the three appearances are at least 44 x 44
(`LinkText`/`Canvas` system colours, so no hue is chosen for a program that has no theme); a `summary` is 44 px; a styled `Text` has a size and a case, no colour of its own except the eyebrow's. **With a theme** the
appearances and roles take its colours: `primary` is `accent_fg` on `accent`, `secondary` and the eyebrow `accent`, `lead`, `note` and `quiet` `muted`, all pairs the theme already checks at 4.5:1.

## 7. `Rich`: inline content (B2)

```
Rich { "A program opens a file. " Strong { "What this shows:" } " " Code { "check" } " found it. See " Link { to: "#docs" "the docs" } "." Break { } "Next." }
Heading { level: 1 "Tools built for agents." Break { } Em { "Not adapted from humans." } }
Figure { Caption { "20 seconds. " Link { to: "https://github.com/alpibrusl/cancho-ui" "cancho-ui" } "." } }
Details { Summary { "The same session as text " Small { "(a real run)" } } Code { "$ cancho check leak.cho" } }
```

| element | becomes | holds |
|---|---|---|
| `Rich { style: .. }` | `<p>` (`data-style` as a styled `Text`) | text and inline elements; `style:` is `"eyebrow"`, `"lead"`, `"note"`, `"label"` |
| `Strong`, `Em`, `Small` | `<strong>`, `<em>`, `<small>` | text and inline elements |
| `Code` inside inline content | `<code>` | text only |
| `Break` | `<br>` | nothing |
| `Link` (inside any of them) | `<a href>` | text and `Strong`, `Em`, `Small`, `Break`, `Code`; **not another `Link`** |
| `Summary` (first child of a `Details`, instead of `summary:`) | `<summary>` | the same inline content |

* **Inline content is also what a `Heading`, a `Caption` and a `Link` hold**: they take text and the same inline elements (the real page has a `<br>` and an `<em>` in its `h1`, `<small>` in a `summary`, links in both
  `figcaption`s: 5.2b item 6). A `Text { .. }` or any block element inside them is `rich-child-invalid` (B1 let a `Heading` hold a `Text` by accident).
* Text goes into the element as **text nodes between the inline elements** (`<p>A <strong>b</strong> c</p>`), not in a `<span>` each. A `For` or an `If` inside inline content is allowed and draws its text in a
  `<span>` per item, which a prerenderer would have to reproduce.
* **The same name, two meanings, by place**: `Code { .. }` directly inside inline content is the `<code>` of a sentence (`InlineCode` in the IR, decided when the view is lowered); anywhere else it is the box of
  section 8. `Strong`, `Em`, `Small` and `Break` anywhere else are `inline-outside-rich`.
* **`Span` was not added**, though the decision listed it: a `<span>` with no attribute says nothing. Measured on the live page: 85 `span`s, **42 of them inside text blocks, and every one of those carries a class**
  (`n`, `chip built`, ..: the numbers and the stage chips of the generated lists), none is a bare span; the three sections measured in 5.2b have none. What those 42 need is a styled inline element (a chip), which is
  not in the closed set and which a `Span` would not give. *(Corrected 2026-10-26: measured in `waffle.md` 1, the 42 spans include 14 chips (built 9, early 2, alpha 2, design 1) and the other classes belong to the page's drawings; `Chip { tone }` is built there.)*
* **`Strong` is `<strong>`**, and the page writes `<b>` (16 times, mostly a name: `<b>cancho</b>`). Both are bold; a screen reader reads them alike; `<strong>` says importance. A parity check against the live page will
  list the 16 as a difference rather than hide it.
* Tags: `rich-child-invalid`, `rich-empty`, `inline-outside-rich`, `code-child-invalid`; a `Summary` outside a `Details`, or beside `summary:`, or not first, is `details-incomplete`.

## 8. `Code`, and the `Clipboard` capability (B2)

```
component Install {
    requires Clipboard;
    view { Code { copy: true max_height: 28 "git clone https://github.com/alpibrusl/cancho\ncargo build -p cancho --release" } }
}
```

* **The DOM**: `<div class="cui-code" data-copy=""><pre tabindex="0" style="max-height: 28rem;"><code>..</code></pre><button type="button" class="cui-copy" aria-label="Copy the code">Copy</button></div>`. The `<pre>` is
  focusable (`tabindex="0"`) so a keyboard user can scroll it; without `copy:` there is no `data-copy` and no button; without `max_height:` no `style`. `max_height:` is an integer from 4 to 100 (rem):
  `code-max-height-invalid`; `copy:` is `true` or `false`: `code-copy-invalid`; the box holds text only: `code-child-invalid`. A brace in the text is written `\{`, as in a `Text`.
* **`Button { copy: field }`** is the same capability for a text the page holds (docs/clipboard.md): the tap writes the text of a `String` state field, and no other code touches the clipboard.
* **`copy: true` is the `Clipboard` capability**: the component declares `requires Clipboard;` (`clipboard-not-declared` if it does not; the existing `capability-unused` if it declares it and has no copy button).
  It is **write only**, and only from a tap by construction: the compiler writes the one call to `navigator.clipboard.writeText` inside the click of the button it draws, and no other code touches the clipboard.
  `inspect effects` lists `Clipboard` under `requires` and `diff` adds it as `+ requires Clipboard` with `authority: expanded` (tests).
* The tap writes the text **as shown** (`pre.textContent`), says "Copied" for 1.5 s, and where the write is refused ("Select and copy") or the clipboard is absent ("Press Ctrl+C") it selects the box so that the keyboard or
  the long-press menu finishes the job. The cancho-www page strips trailing `# comments` from what it copies; that is the page's own rule and is not reproduced: a parity check will list it.
* **Measured** (Chromium, `Pixel 7` profile, clipboard permission granted): nothing writes to the clipboard at load or at a render; a tap writes the text of the box once and reading it back gives the same text; the page
  calls `readText` 0 times; with `writeText` rejecting, the label is "Select and copy" and the text is selected; with `navigator.clipboard` undefined, "Press Ctrl+C" and the text is selected; the button is at least
  44 x 44 and named. The emitted module of a program with no copy button has no clipboard code at all, and one with it has one `writeText(` (tests).
* **Looks**: the box is dark in both schemes, `#12151a` with `#d6dde8` (13.39:1) by default and `code_bg`/`code_fg` with a theme (drawn at 13.39:1 in both schemes of the site's palette); the copy button keeps the
  baseline's 44 px target and sits in the corner; `pre` has room for it (`padding-right`).
* **Not measured**: a real phone's long-press menu; iOS Safari's rule that `writeText` needs the tap itself (the call is inside the click handler, which satisfies it, but no iPhone ran it); a screen reader announcing
  "Copied" (the label changes text, with no live region: a person who cannot see it is not told: **a gap**, noted for a later pass).

## 10. `Image`, `Media`, `ratio`, `Grid` (B3)

```
Grid {
    min: 17
    gap: 3
    Figure {
        Image { src: "assets/img/field.webp" fallback: "assets/img/field.jpg" alt: "A field of boulders." width: 1024 height: 768 ratio: "4:3" }
        Caption { "A field of boulders." }
    }
    Figure {
        Image { src: "assets/img/dawn.webp" fallback: "assets/img/dawn.jpg" decorative: true width: 1024 height: 768 ratio: "4:3" }
        Caption { "First light." }
    }
}
Grid { min: 19 weights: [1, 1.75] gap: 3 Column { Text { "the text" } } Column { Code { "the code" } } }
Figure {
    Heading { level: 3 "cancho-ui: a component declares what it may do" }
    Media {
        label: "cancho-ui demo"
        kind: "video"
        src: ["assets/media/ui-demo.mp4", "assets/media/ui-demo.webm"]
        poster: "assets/media/ui-demo.poster.jpg"
        ratio: "16:9"
        caption: "cap2"
        transcript: "demo-text"
    }
    Caption { id: "cap2" "20 seconds: real compiler output beside the compiled counter running." }
}
Details { id: "demo-text" summary: "The same session as text" Code { "$ cancho-ui check counter.cui" } }
```

### 10.1 Corrections to `www.md` 5.2, made there too

The design had four things that the build showed to be wrong or unfinished; each is corrected where it was said (`www.md` section 5.2 and table 5.2b row 4):

* `fallback: ".jpg"` (a suffix) is **`fallback: "assets/img/field.jpg"`, a path**: the compiler has to find the file to check it exists, to hash it, and to copy it, and a suffix is not a file.
* `alt-source:` does not exist. A video's text alternative is **`caption:`** (the `id` of a `Caption`, which becomes `aria-describedby`) and/or **`transcript:`** (the `id` of any element with an `id:`, which becomes
  `aria-details`), at least one: `media-text-alternative-missing`. Both are text literals naming an id of the program, not bare names.
* A `Media` also has a required static **`label:`**, which the design did not have: it is the accessible name of the player and the text of the one link inside `<video>` (see 10.3). Without it a video is named by
  nothing; `media-label-missing`.
* The weighted grid's `min:` is not the `min` of the equal one: with `weights: [1, 1.75]` it is the width of the *weight 1* column, so the line needs `Σ weights x min` rem. 5.2b row 4 guessed `min: 25` from
  arithmetic on equal columns and said so (not measured); the measurement (10.4) is **`min: 19`**.

### 10.2 `Image`

* **The DOM** (one recipe, `cancho_ui_ir::media::image_dom`; the prerenderer will read the same function):
  `<picture class="cui-img" data-ratio="4:3" style="max-width: 1024px;"><source srcset="assets/img/field.webp" type="image/webp"><img src="assets/img/field.jpg" width="1024" height="768" alt=".." loading="lazy" decoding="async"></picture>`.
  `<source>` only when there is a `fallback:`; `data-ratio` only with a `ratio:`; `loading="eager" fetchpriority="high"` instead of `lazy` with `priority: true`.
  The page's own markup is the same (`<picture><source type="image/webp" srcset=..><img src=.jpg width height alt loading="lazy" decoding="async"></picture>`, 5 of them); the `class` and the `style` are ours.
* **`alt` or `decorative: true`, never neither, never both**: `image-alt-missing` (neither, an `alt` of spaces, `decorative: false`), `image-alt-conflict`. A decorative image is `alt=""`, which is how
  Chromium leaves it out of the accessibility tree (measured). `width` and `height` are required integers from 1 to 10000: `image-size-missing`, `image-size-invalid`. `ratio:` is one of `1:1 4:3 3:2 16:9 21:9 3:4 2:3`
  (`ratio-invalid`). `priority: true` is for the one picture the reader sees first (`image-priority-invalid` for anything but `true`/`false`); every other image is lazy.
* **`src:` and `fallback:` are files of the site, written relative to the program**: letters, digits, `. _ - /`, no `..`, no empty segment, no leading `/`, at most 200 characters, in png, jpg, jpeg, webp, avif
  or gif (**not SVG**, which can carry script), and the fallback is another file in another format (`image-src-invalid`). An address of another host is refused with the reason: a page makes no request to another host.
  A `src:` that is a state field is a parse error: the value is a literal (a picture chosen by data is not offered).
* **Looks**: the picture is a block, as wide as its column and never wider than the file (`max-width` is the `width:`); with a `ratio:` it is cropped to the shape (`aspect-ratio` on the `picture`, `object-fit: cover`
  on the `img`), with rounded corners and no other chrome. The theme does not touch it.
* **No layout shift** (measured): with a picture that arrives 1.2 s late the box is the same height before and after (`width` and `height` give the browser the aspect ratio before the file is there).

### 10.3 `Media`

* **The DOM**: `<video class="cui-media" data-ratio="16:9" aria-label="cancho-ui demo" controls playsinline preload="metadata" poster=".." aria-describedby="cap2" aria-details="demo-text"><source src=.. type="video/mp4"><source src=.. type="video/webm"><a href="first source">cancho-ui demo</a></video>`.
  `controls`, `playsinline` and `preload="metadata"` are always there; **there is no way to write `autoplay`, and no key for it** (a key that does not exist is not a rule: `binding-unknown`), and a video the program does not
  start does not start (measured: after its metadata loads, `paused` and `currentTime` 0). `kind:` is `"video"` (`media-kind-invalid`; audio is not offered). `src:` is one text or a list of one to four files
  in mp4 or webm, no repeats (`media-src-invalid`); `poster:` an image of the site (`media-poster-invalid`); `ratio:` as for an image.
* **The text alternative is required**: `media-text-alternative-missing`. `caption:` must be the `id` of a `Caption` of the program, `transcript:` the `id` of any element with an `id:` of it, both checked over
  the whole program (`media-reference-invalid`: no such id; or a caption that names a `Details`). The `Caption` stays a child of its `Figure`, where `caption-misplaced` already holds it.
* The `<a>` inside `<video>` is the fallback for a browser that cannot play video at all; it names the video and leads to the first file. **Not measured** in a browser without video support (none was available).
* Offline: `--pwa` keeps the pictures and the poster in the cache and **not the videos** (10.5).

### 10.4 `Grid`, measured against the cancho-www page

`Grid { min: M }` is `display: grid; grid-template-columns: repeat(auto-fit, minmax(min(100%, Mrem), 1fr))` (`min:` an integer from 8 to 60, `grid-min-invalid`; `gap:` 0 to 4 as on a `Row`). With
`weights: [..]` (two to four numbers from 1 to 4 with at most two decimals, **one for each child, and the children written out**: no `For`, no `If`: `grid-weights-invalid`) it is a wrapping flex line whose cell *i* has
`flex: w_i 1 min(100%, w_i x M rem)`: when the line holds `Σ w_i x M` rem and the gaps the cells share the width in proportion to the weights, and when it does not they stack, one under another, each the full width.

Measured in Chromium (`Pixel 7` profile) by `scripts/measure-www-grid.js` on the cancho-www clone at `dbbf7ae`: for 16 viewport widths from 320 to 1440 the page's grid is measured (the width of its content box, its column
gap, its columns) and ours is put in a box of that width with that gap:

| the page | ours | 16 widths |
|---|---|---|
| `.videos`: `repeat(auto-fit, minmax(22rem, 1fr))` and a 30 rem rule | `Grid { min: 22 }` | **same column count at 16 of 16; column widths equal to 0.0 px** |
| `.gallery`: `repeat(auto-fit, minmax(17rem, 1fr))` | `Grid { min: 17 }` | **16 of 16; 0.0 px** |
| `.try article`: `1fr 1.75fr` from 60 rem (a viewport rule) | `Grid { min: 19 weights: [1, 1.75] }` | **14 of 16 the same count, 0.1 px at most in a width** (308 + 539 at 960, 331 + 579 at 1024, 378 + 661 at 1280 and 1440, the page's numbers); at 950 to 959 ours is two columns where the page is still one |

So the weighted grid reproduces the page's `.try` columns to a tenth of a pixel, and **its breakpoint is 10 px early** (viewport 950 for 960): the page changes at the viewport, `60rem`; ours changes when the
grid is `2.75 x 19 rem + gap` wide, and `min` is a whole number of rem (`min: 20` would be 34 px late, at 994). The two were not made to agree by adding a viewport rule, because a `Grid` has none; the difference is reported,
not hidden. Other differences, known: one `gap` for both directions (the page's `.try article` has a row gap of 1.1rem and a column gap of 1.8rem); the page's `.videos` has its own rule below 30 rem that `min(100%, ..)`
makes unnecessary (same widths at 320 to 480 in the table).

Also measured by `check-structure.js` part F against a formula written in the check (not the CSS's own algorithm): the number of columns of a `Grid { min: 17 }` of five items and of a `Grid { min: 22 }` of two
(the row is filled: empty tracks collapse) at 12 widths from 320 to 1440; the weighted grid is 1 : 1.75 within 1.75 px side by side and stacked full width below `Σ w x min` plus the gap, and **changes at exactly the width
the formula says (within 1 px)** found by bisection over the viewport; three weights `[1, 2, 4]` are 1 : 2 : 4 when they fit on one line; at 320 px nothing scrolls sideways. **Three or four weights between "all on a
line" and "stacked" wrap as flex does (two and one, say), which `auto-fit` also does** and no check pins; the page's six asymmetric grids with a breakpoint at a viewport width are for the cases of 5.3.

### 10.5 Files: the asset pipeline

* `check` and `build` read every file the views name, once: it is a file **inside the directory of the program** (a symbolic link out of it is `asset-missing`: the real path is what is compared), at most **20 MB**
  (`asset-too-large`), and begins as its extension says (`asset-type-mismatch`: the first bytes of png, jpg, gif, webp, avif, mp4 and webm; a file only renamed is caught, a corrupt one that begins correctly is not).
  `asset-missing` also covers a directory named like a file and an unreadable file. Paths are relative to the **entry file's** directory, also for a component imported from another file.
* The SHA-256 and size of each file are in the IR (`assets`, only when there are some) and `diff` reports `~ file assets/a.webp: <12 digits> -> <12 digits>`, `+ file`, `- file`, in JSON `assets: [{path, base, candidate}]`
  (absent when none changed); a changed file is a change of the program (`change_count`) and is not a change of authority. Replacing a picture with another of the same name is therefore a line in review.
* `build --page` and `--pwa` copy the files the views name, at the same paths, into the output (a file no view names is not copied). `--pwa` puts the pictures and posters in the offline cache and **not the videos**
  (a 20 MB video would be most of the install), and the cache name still moves when a video changes (tests).
* **Cost**: `check` reads and hashes what it names every time: a 20 MB mp4 takes 2.0 to 2.2 s in the debug binary (three runs, this machine); a release build was not measured. The cancho-www home page names (`ls`) 8 picture files (924 kB), 2 posters (187 and 58 kB) and 4 video files (124 to 617 kB, 1,443 kB together): none near the bound, and 2.6 MB of files for `check` to read.
* **Authority**: none. A picture or a video is a file of the site, requested by the page of its own origin; no `Network` is declared or needed. The built module of the example has no `fetch(` and no address of another
  host; a Chromium run of part F records every request of the page and finds none to another origin. `inspect effects` and `diff` show `authority: unchanged` for a program that gains pictures, video and grids (tests).

## 12. The roles of the look (2026-10-29)

Designed and measured in [`www-port/look.md`](www-port/look.md): what the cancho-www page's look needed that the language could not say. Five small additions, each a declared role with the CSS in the compiler:

* **`card: true`** on a `Section`, `Article`, `Aside` or `Figure`: the class `cui-card`; on a **`List`** the list is a grid of cards (`cui-cards`: `repeat(auto-fit, minmax(min(100%, 13rem), 1fr))`, each `li` a card, markers inside). The baseline gives it padding (1.1 / 1.2 / 1.3 rem), a 16 px radius and a 1 px edge; **a theme** gives it the `surface` fill and the shadow the link buttons already use (a 1 px `line` ring in the dark scheme). `card-invalid` for anything but `true` or `false`; `binding-unknown` on any other element. Under `page { scale: "display" }` a heading of level 2 inside a card is set at the h3 size, as the page's card titles are.
* **`align: "center"`** on a `Grid` (the default is `"stretch"`): the class `cui-align-center`, `align-items: center`. A Grid is the language's two-column row that stacks (`Grid { min: 26 .. }` is two columns where two of 26 rem fit and one where they do not), so a hero or a text beside a code box is a Grid and this key. `grid-align-invalid`.
* **`appearance: "pill"`** on a `Link`: a small rounded link with a dot, drawn 30 px tall and a 44 px target (a transparent 7 px border is the target, an inset shadow the edge); in a theme it is the `warn` pair (`warn` on `warn_bg`, checked, with `warn_line` as the edge).
* **A `Row` that is a child of a sticky `Header` is its end group** (`margin-inline-start: auto`): the brand and a `Chip` at the start, a GitHub link and the menu at the end. In a theme the header is the page's colour at 86 % over a 10 px blur with a soft shadow (a hairline in the dark scheme), and its first link is the brand (the theme's mono font, bold).
* **`page { measure: ".."; scale: ".."; }`** ([`page.md`](page.md) section 3): the centred column and the display scale.

Measured by `scripts/pixel-diff-www.js`: [`www-port/look.md`](www-port/look.md) section 6 (mean 33.8 % to 29.7 %).

The baseline rules of the first three are written **only for a program that uses one** (`cancho_ui_ir::page::uses_look_roles`), so every other page, and every committed gallery demo, is the bytes it was; the rule of the end group is in the sticky header's own `<style>`.

### 12.0 A link to the backend (2026-11-09)

A program that signs a person in through a provider has to send the browser to its own server (`/api/auth/google/start`), which answers with a redirect: a navigation, not a file, and not an address of another host. `Link { to: "/api/..." }` is that. `/api/` is the prefix the console's own requests already use (`docs/mobile-backend.md`), so the compiler writes the path as it is, with no file to carry and no host to list.

* The path is letters, digits, `-`, `_` and `/`: no dot, no query, no fragment, no empty segment, at most 128 bytes (`link-route-invalid`). A query is the server's business, not the page's.
* Everything else about a link is as before: it needs text, and `rel` and the target are what a same-origin link gets.
* Guarantee tier: `static` for the shape of the path; that the server answers there is not known here.

### 12.0a A Button in a Nav is a tab (2026-11-09)

The console's navbar (Home, Trips, Groups, Me) is a `Nav` of `Button`s whose open one says `pressed:`. A link cannot be used there: the sticky header hides the links it holds under a width (measured: `display: none` at 390 px), and a `Nav` that is a direct child of a sticky `Header` is hidden under 62 rem. So, **in a page that uses a look role** (the rules below are written only then, like the others of section 12): a `Button` inside a `Nav` is drawn without its fill (the theme's `fg` on the page), and the one with `aria-pressed="true"` is filled (`accent`, `accent_fg`, a checked pair) with no ring. Everywhere else a button is what it was. Guarantee tier: `tested` for the rule's presence (`crates/cancho-ui/tests/look.rs`); the look was seen in the browser pane at 390 px, not measured.

### 12.0b A docked Nav is the tab bar (2026-11-09)

`Nav { label: "Main" dock: true Button { .. } .. }` is the bar at the foot of the window that phone apps use for their main places. It is `position: fixed`, centred, at most 28 rem wide (the window less 1 rem on each side), a pill with a blurred `Canvas` behind it, a shadow and the safe-area inset under it; its children share the width equally. The page keeps `5.5rem` of room at its foot (`body:has(.cui-dock)`), so the last thing on the page is not under the bar. Its `Button`s are tabs as in 12.0a.
* `dock:` is `true` or `false` as a literal (`nav-dock-invalid`); a page has one docked `Nav` (`nav-dock-duplicate`); the key is taken by a `Nav` only.
* Guarantee tier: `tested` for the rules and the CSS text (`crates/cancho-ui/tests/look.rs`); the look is for the browser pane.

### 12.0c An avatar (2026-11-09)

`Text { style: "avatar" "EA" }` is the initials of a person (two letters, upper-cased by the page) on a 2.25 rem round disc with a 2 px ring of the page's own background. Side by side in a `Row` the discs overlap by 0.6 rem, and their colours go coral, plum, green, amber-brown, by position (`#b41d26`, `#6b5585`, `#1e7e34`, `#884e00`: each is at least 4.5:1 against the white text, computed, not looked up). Guarantee tier: `tested` for the CSS text (`tests/look.rs`).

### 12.0d A cover card (2026-11-09)

`Column { card: true overlay: "cover" Image { .. } Column { .. } Text { .. } Row { .. } }`: a card with the **picture on top** (16:10, cropped to fill), the **second child over the foot of the picture** on a dark scrim (white text: a title, dates, a chip), and **every later child as the panel under the picture** (padded 1.1 rem, with room above the first and under the last). The card is 24 px round and, in a page with a theme, takes the surface colour and shadow. It is the photo-over-panel card of travel and social apps; `overlay: "banner"` (everything over the picture) is still there. `overlay:` is `true`, `false`, `"banner"` or `"cover"` (`overlay-invalid`). The white text over the picture is only as readable as the picture: the scrim is black at 70 % at the foot and 0 % at the top of the second child, and the check of the picture's contrast is the author's. Guarantee tier: `tested` for the CSS text (`tests/look.rs`).

### 12.0e Fields (2026-11-09)

In a page that uses a look role a `TextField`, a `Select` and a `TextArea` are no longer a square box: an input and a select are a **pill** (999 px, 1.1 rem each side), a text area has 20 px corners, and with a theme a field is filled with `soft` (not `surface`, which is a card's own colour, so a field inside a card showed only its border). The border stays one thin line at `muted`, which is what keeps a field's edge at 3:1 against the page (WCAG 1.4.11): a softer border would look more like the design this came from and would fail that. The focus is a 3 px ring of the accent at 55 % beside the browser's own outline, with the border in the accent. Guarantee tier: `tested` for the CSS text (`tests/look.rs`); the look was seen in the browser pane only.

### 12.0f A disclosure (2026-11-09)

In a page that uses a look role the `summary` of a `Details` is a pill (the same 44 px, 1 px `muted` border and 999 px corners as a field) with a "+" before the text that becomes a "−" when it is open, and the browser's own triangle is hidden; the inside has 0.75 rem above it. The summary of a `Chart`'s data table (`.cui-chart`) and the hamburger of a sticky header keep their own styles. It reads as something to press, which a bare line of text does not: a form behind it ("Start a group") is no longer mistaken for a heading. ### 12.0g A floating button and a sheet (2026-11-09)

`Aside { label: "Chat" fab: true Button { .. } }` is a **floating button**: fixed at the end of the window above the tab bar, so it stays where it is when the page scrolls. `Aside { label: "Group chat" sheet: true .. }` is a **sheet**: a panel fixed over the foot of the page (28 rem wide at most, 24 px corners, scrolling inside when it is taller than the window less the bars), a flex column of what it holds. Neither is drawn by the page's script when it appears: both are in the page's own HTML, so **an island can sit inside a sheet** (the rule that an island is outside every `If` and `For` holds; the sheet is neither).
What shows or hides them is a **marker**: an empty `Aside { marks: "fab" }` or `Aside { marks: "sheet" }` that the program draws inside an `If`. The button is shown while a `"fab"` marker is on the page and the sheet while a `"sheet"` marker is (`:root:has([data-mark=".."])`); a marker is never drawn itself (`[data-mark] { display: none }`), so it is not a landmark. A program says "open" by making the `If` true and "close" by making it false: state, so it survives the redraws a `Details` does not.
* One button and one sheet to a page (`aside-fab-duplicate`, `aside-sheet-duplicate`); each needs a marker of its kind somewhere in the program (`aside-unmarked`: it would never be seen); `fab:` and `sheet:` are `true` or `false` (`aside-flag-invalid`); `marks:` is `"fab"` or `"sheet"` (`aside-mark-invalid`); the keys belong to `Aside` only (`binding-unknown` on anything else).
* **What this is not:** a modal. Nothing behind it is made inert, focus is not trapped and Escape does not close it: a sheet is a panel you can leave open while you read the page. The program gives it a close button.
* Guarantee tier: `tested` for the rules and the CSS text (`tests/look.rs`); the look and the marker working at run time are for the browser pane.

### 12.0k A second floating button, a second sheet and a band (2026-11-13)

A group page needs two floating buttons (the chat, and "new trip") and two panels (the chat, and a small form or a settings sheet), and 12.0g allows one of each. `Aside { fab2: true Button { .. } }` is a **second floating button**: fixed at the start side of the first one, same height, round; while it is on the page the first button is given a minimum width of 4.5 rem so that the two never overlap whatever the first one holds. `Aside { sheet2: true .. }` is a **second sheet**, the same panel as 12.0g's (28 rem, 24 px corners, scrolls inside, the first row is a title and a quiet close button) without the chat's log rules. While the second sheet is shown, **both floating buttons are hidden** (they would sit over it). They are shown by the markers `Aside { marks: "fab2" }` and `Aside { marks: "sheet2" }` drawn inside an `If`, as in 12.0g.
`Aside { band: true .. }` is a **band**: a block in the page's flow (not fixed) that a marker `Aside { marks: "band" }` shows and hides. It exists because a sealed island may not sit under an `If` (`island-rebuilt`) and so cannot appear and go with a screen: put in a band it is in the page's own HTML and the marker decides whether it takes any room. One to a page (`aside-band-duplicate`).
* One of each to a page (`aside-fab-duplicate`, `aside-sheet-duplicate`); each needs a marker of its own kind (`aside-unmarked`); `Text { style: "star" "★" }` placed right after an avatar is a small white disc on its lower corner (the organiser's mark on a member's circle: 0.95 rem, the glyph at least 4.5:1 on white); the next avatar overlaps as it does without it. `fab2:`, `sheet2:` and `band:` are `true` or `false` (`aside-flag-invalid`); `marks:` is one of the five (`aside-mark-invalid`).
* **Not a modal, and not exclusive:** nothing stops a program from showing both sheets at once, and they would overlap. The program shows one at a time.
* Guarantee tier: `tested` for the rules and the CSS text (`tests/look.rs`); the look is for the browser pane.

### 12.0l A person's own picture on a disc, and a second band (2026-11-13)

Profile pictures (cancho-ota docs/design.md 30.103) need a disc that shows a photo the server holds as text, a colour and an emoji, or the initials, in every place a person's initials were drawn. Nothing else about the discs changes: a `Text { style: "avatar" "AR" }` is drawn as it was.
* **`face(initials, tone, emoji, photo)`** (docs/lists.md 7.2d) is a String; put as the text of a `Text { style: "avatar" .. }` or `"disc0" .. "disc7"`, the page draws the disc from its four parts: the **emoji** in place of the initials when it is 1 to 16 UTF-16 units (else the initials; a larger glyph, `data-emoji`), the **tone** (`"0"` to `"11"`, else none) as a `data-tone` that picks one of **twelve fixed colours** (the eight of 12.0i and `#475569`, `#4338a0`, `#7b2d8e`, `#0e6b8c`: each 6.00:1 or better with the white text, computed with the WCAG formula, the same in both schemes; the rule has the weight of the two-attribute rules so it wins over the disc's own colour), and the **photo** (base64, 100 to 48,000 characters, starting `/9j/` like a JPEG, only the base64 alphabet: anything else is not drawn) decoded by `createImageBitmap` and drawn on a canvas that covers the disc (`.cui-face-pic`, round, `aria-hidden`; the text under it stays for a reader of the screen). **No `<img>`, no address, no request, no `data:` URI and no `innerHTML`**: the parts are text nodes, so the page's policy needs nothing new and nothing a person writes can be read as markup. A photo that does not decode leaves the text. Decoded photos are kept by their text (at most 120, then the cache is emptied).
* **What decides who is shown what is the program's, not the toolkit's:** the toolkit draws the four strings it is given. (cancho-ota gives a person's photo only when the server says the viewer may see it.)
* **`Aside { band2: true .. }`** with **`Aside { marks: "band2" }`** inside an `If` is a **second band**, the same block in the flow as 12.0k's, shown only while its marker is on the page; one to a page (`aside-band-duplicate`), and it needs its marker (`aside-unmarked`). It exists because the profile picker is a sealed island that is on the page only while it is open, and an island may not sit under an `If`. `marks:` is now one of six (`aside-mark-invalid`).
* **Not built:** a photo drawn from a program's state anywhere but on a disc; a larger or non-round picture; an image format other than JPEG.
* Guarantee tier: `tested` for the rules, the CSS text and the page script (`tests/look.rs`, which runs `__cui_face_draw` under node with a stand-in document); the drawing was seen in headless Chrome at 390 px in both schemes (cancho-ota docs/design.md 30.103).

### 12.0h A chat: a log, bubbles, a composer (2026-11-09)

Three flags of two elements make a messenger's layout, with nothing it needs from a script but one rule:
* **`Column { chatlog: true .. }`** is the log: a column that scrolls inside itself (`overflow-y: auto`, 9 rem at least, soft fill, 18 px corners). **A log that was at its foot stays at its foot when a message is added** (within 48 px of it before the render); one the reader scrolled up keeps its place. The emitted script reads each log's place before a render and sets it after, before the focus is given back; a page with no log has none of it.
* **`Column { bubble: "mine" | "theirs" | "system" .. }`** is a message: at most 82 % wide, 16 px corners with the corner nearest its side at 4 px, `surface` for theirs (at the start), `accent_soft` for mine (at the end), no fill and centred for a system line. Inside, a `Text { style: "eyebrow" }` is the author's name (not upper-cased, 0.78 rem, bold) and a `Text { style: "note" }` is the time (0.68 rem, at the end).
* **`Row { composer: true TextField { .. } Button { .. } }`** is the box to write in: the field takes the width and shows no label (its `aria-label` and `placeholder:` are what name it), and the **last `Button` is a round 46 px send button** with the glyph ➤ in place of its text (the label stays its accessible name).
* A `Button` inside a bubble is a small quiet pill (28 px high, an outline, the accent as its text: above the 24 px of WCAG 2.5.8, below the 44 px of the page's own buttons, on purpose, so a row of reactions does not outweigh the message). The first row of a sheet is a title at the start and its button at the end, also quiet.
* In a sheet (12.0g) that holds a log, the sheet has a height of 34 rem at most (the window less the bars) and does not scroll as a whole: the log does, and the composer stays under it.
* `bubble:` is one of the three (`bubble-invalid`); `chatlog:` and `composer:` are `true` or `false` (`chat-flag-invalid`); the keys belong to `Column` (`bubble`, `chatlog`) and `Row` (`composer`) only.
* **Not here:** a picture or a voice note in a bubble (a picture's address is a literal), reactions on a long press, read ticks, a day heading, "typing". Guarantee tier: `tested` for the CSS text and the script (`tests/look.rs`); the look is for the browser pane.

### 12.0i A chat that reads like a messenger's (2026-11-13)

What 12.0h left out, in the shape of a group chat on a phone. Every key is a literal checked at build; nothing here needs free CSS.
* **A run of one sender.** A bubble that starts a run has, as its first child, `Text { style: "mark" "." }` (never shown: the CSS reads it with `:has`): the bubble then gets a **tail** (a small triangle at its top corner on the side it leans to, the corner itself square), more room above (0.5 rem; a bubble inside a run has 0.12 rem). The first bubble of a run of someone else's messages also holds, before its text, **`Text { style: "disc0" .. ### 12.0j Replies, mentions and ticks in a chat bubble (2026-11-13)

Part two of the messenger look (12.0i): what a bubble needs once the server sends quotes, mentions and read ticks (cancho-ota docs/design.md 30.101). Nothing here needs free CSS or a new capability.
* **`Column { quote: true .. }`** inside a bubble is the **quote** of an earlier message: a block with a rule (4 px) at its start in the colour of the person quoted, a soft fill, and its children as they are. The rule's colour is taken from the name inside it: a `Text { style: "hue0" .. "hue7" }` in the block sets the rule to that hue (the same eight colours as 12.0i, light and dark: `:has([data-style="hueN"])`), so the program picks the hue once, for the name, and the rule follows. A `Text { style: "note" }` in the block is **one line, cut with an ellipsis** and a little larger than a note of the bubble. `quote:` is `true` or `false` (`chat-flag-invalid`) and belongs to `Column` (`binding-unknown` on a `Row`).
* **`mark_text(text, marks)`** (docs/lists.md 7.2b) and **`Text { style: "marked" .. }`** are the **mention highlight**. `marks` is a JSON array of `{"start":n,"end":m}` **byte offsets (UTF-8) into `text`**, which is what the server sends for `@handle` (a page cannot slice a text by byte offsets, and a program that cut by characters would be wrong after an accent or an emoji). `mark_text` returns the text with each marked part between U+E000 and U+E001; `style: "marked"` makes the page cut the text at those two and draw each part between them as a `span.cui-mention` (a rounded pill on a tint of the accent, bold). The page builds the pieces with text nodes and `textContent`, **never as markup, and `innerHTML` is not used** (a test reads the page script for it), so nothing a message says can be read as HTML. A mark that is empty, backwards, past the end, starts before the end of the one before, or does not begin and end on a character boundary is skipped; `marks` that is not such an array leaves the text as it is; the two private-use characters are removed from the text itself first, so a message that contains them draws no pill of its own. The program passes the array as `"[" + join(json.items(m, "mentions"), ",") + "]"` (`json.get` of an array answers its default, `json.items` answers each element as JSON text). Replay's `mark_text` and the page's `__cui_mark_text` are the same function written twice; `tests/look.rs` runs the page's against node on the same cases (skipped with a note when there is no node).
* **`Row { meta: true .. }`** is the line at the bottom end of a bubble that holds the time and the ticks side by side (the bubble's text and the time are in one column; this row puts the ticks next to the time); **`Text { style: "tick" }`** (muted) and **`Text { style: "tickblue" }`** (`#1d5fa8` light, `#7db5ff` dark: the same blue as the `hue5` name, 6.45 and 8.06 against the bubble) are the glyphs, drawn tight (`letter-spacing`) at 0.72 rem. The toolkit draws them; **what they say is the program's** (the server's `ticks`: 1 stored, 2 read by everyone who shares).
* **`Row { strip: true .. }`** in a sheet, under the log and above the composer, is a **one-line strip**: the first text is cut with an ellipsis, buttons are small pills (1.9 rem) that do not wrap, the row does not shrink when the log is long. It holds "replying to .." with its cancel and the list of people an `@` can name; a row of the sheet that is not a strip is still the wrapping emoji tray of 12.0i.
* **Refused, with their tags:** `quote:` on a `Row`, `meta:` or `strip:` on a `Column` (`binding-unknown`), a flag that is not a boolean literal (`chat-flag-invalid`), a style outside the closed list (`text-style-invalid`, which now also lists `marked`, `tick`, `tickblue`), `mark_text` with other than two arguments.
* **Not built (D)** *(pictures: corrected 2026-11-16, 12.0r: `Photo` draws a picture from state, with its mime fixed by the check of the text (`/9j/` at first; a JPEG, a PNG or a WebP from 2026-11-17, by their signatures) and no `data:` address, so no `img-src data:` entry for it and no `media-src`; the page's policy is the baseline of every page. Voice notes: built 2026-11-16, 12.0t: `AudioField` records one and `AudioClip` plays one from state with the engine's decoder, so the policy needs no `media-src` either)*: pictures and voice notes **inside the bubble**. `Image` takes only a literal path of the site (`image-src-invalid`), there is no audio element, and a chat's media need the bearer token, so the page itself would have to fetch each one and hold its base64 in state (up to 36 KB each, 60 in a window) and redraw it at every five-second poll; an island cannot sit under an `If` or a `For` (docs/islands.md) and is sealed from the network. Doing it safely is a new element that draws a `data:` image or sound from program state, with its mime checked against a closed list, `img-src`/`media-src` `data:` in the page's policy and its own `authority` line; that is a toolkit change in six crates and its own review, not done here.
* Guarantee tier: `tested` (`tests/look.rs`, replay's `chat_builtins`); seen in headless Chrome at 390 px in both schemes (cancho-ota docs/design.md 30.101).

### 12.0m A flat tab bar, keys, hints and a bar of places (2026-11-13)

Read on a real phone, the console's buttons were too heavy: the open tab of the dock had a thick dark edge, every icon-only button was a 46 px red disc on a line of its own, the "i" that opens a note was a "+" pill, and eleven unlabelled icons in a grid were the trip's sections. Four rules, all in the look roles (a page that uses one), all `tested` for their CSS text and flags (`tests/look.rs`), seen in a browser at 390 px, not measured.
* **The dock is flat.** `:root .cui-dock button` has `border: 0; box-shadow: none`. The edge was not a shadow: 12.0a gave the open tab a border *colour* (`theme.rs`), and a button's default border *style* is `outset`, which a browser draws as a 3D edge. A tap's focus ring is dropped (`:focus:not(:focus-visible)`), the keyboard's is kept.
* **An icon-only button is marked** with the class `cui-ico` by the emitter (a `Button` or `NavLink` whose content is its children). It is a class because `:has()` cannot be nested: `.cui-col:has(> button:has(> *))` is not a selector, and a browser drops the whole rule without a word (found when the first version did nothing).
* **Keys.** `Row { keys: true .. }`, and any `Column` or `Row` that holds a `cui-ico` button directly (outside a bubble, chat log, composer, chip row, sheet, band, the dock or a bar) lays its children in one wrapping row: a button is a **key**, 2.5 rem high with 12 px corners on the `soft` fill (the open one in the accent tint, no ring), and the other children of a column take the whole line, in their order. So a stack of round buttons is a row of keys without the program changing. A key whose button has a second `Text` child shows it as a tiny caption under the icon (the `label` is still the accessible name and the tooltip). A `Row { keys: true }` inside a `Row` goes to the end of it. 2.5 rem is under the 44 px of the page's own buttons and over the 24 px of WCAG 2.5.8; the chat's quiet pills are smaller still.
* **Hints.** `Details { hint: true summary: ".." }` is a small round summary (no "+", no border), the note opens under it; in a keys row an open one takes its own line.
* **A bar of places.** `Row { bar: true Row { Button .. } Row { Button .. } }` is one row that scrolls sideways (no scrollbar, snap), each `Button` an icon over a caption (two `Text` children) with `pressed:` filling the open one; each nested `Row` is a group, divided from the next by a hairline. A page is drawn again at every render, which would send a scrolled bar back to its start, so the emitter keeps each bar's scroll through a render, and scrolls a bar to its open place when that changes (`__cui_bars_save` / `__cui_bars_restore`, emitted only in a program that has a bar).
* Refusals: `keys:` and `bar:` belong to `Row` and `hint:` to `Details` (`binding-unknown` elsewhere); each is a boolean literal (`chat-flag-invalid`).
* Not done: a bar does not announce that it scrolls beyond a half-cut item at its edge; a key's caption is not translated by the toolkit (the program writes it).

### 12.0p Steps, a month, tick rows and a foot (2026-11-14)

A console flow was redesigned as three steps by a designer who did not know the toolkit: a progress bar of equal segments, a month calendar where one tap on day 1 marks a range, rows of people with a disc and a tick, and Back/Continue that stay in reach. None could be said before; each is now one flag on a `Row` (in the look roles, so a page that uses one; CSS in `pwa.rs`, `tested` for its text, flags and refusals in `tests/look.rs`, seen in a browser at 390 px, light and dark, by the console's own checks).
* **`Row { steps: true }`** holds `Text { style: "seg" "Step 2, to come" }` for each step not reached and `Text { style: "segon" "Step 1, open" }` for each reached or open one: a thin bar of equal segments (the accent for `segon`). Two new text styles, `seg` and `segon`. The words in a segment are for a screen reader only (the segment is 0.3 rem high with `font-size: 0`); the program writes a visible "Step n of 3" itself.
* **`Row { month: true }`** is a grid of seven columns. A `Text { style: "label" }` is a weekday's heading, an empty `Text { "" }` a blank before the 1st, a `Button` a day, 44 px high with a round 44 px end. `pressed:` tints the days of a range; **a day whose button has a second child (a caption such as "start") is the first day of it**, filled with the accent. The range is therefore not colour alone: the caption marks the first day and the program puts "day 2 of 4" in the other days' labels. The toolkit draws the grid; **the program does the calendar** (the console counts days from 1970-01-01 with `+ - * floor`: no date type, no new builtin, and the one `Clock` it needed is a capability the page now asks for, only to open on this month).
* **`Row { ticks: true }`** is a list of rows, one for each `Button`: a disc (or an icon) first, the text last (the last child takes the room), and a round box at the end that holds a tick when the button is `pressed:`. A row is at least 3.25 rem high and divided from the next by a hairline. Several ticked (people) or one at a time (a choice of stay) is the program's rule; a `disabled:` row stays at full strength (the organiser, who always comes). The tick is the box's `::after` (a character, not an emoji); ticked and unticked differ by the tick and the fill, not by colour alone.
* **`Row { foot: true }`** is a row of keys (as `keys: true`) that stays at the bottom of its sheet while the sheet scrolls (`position: sticky`, on the sheet's fill, over a hairline). Found by use: at 390 x 844 the calendar pushed Back and Continue under the fold of the sheet in dark mode.
* **The generic key rules of 12.0m now leave a month and a tick list alone** (`:not(.cui-month)`, `:not(.cui-ticks)` in each of the long selector chains): a first version of the month drew as a flex row because `:root .cui-row:has(> .cui-ico)` is more specific than any single class (found in the browser, not by the CSS test).
* Refusals: `steps:`, `month:`, `ticks:` and `foot:` belong to `Row` (`binding-unknown` elsewhere) and are boolean literals (`chat-flag-invalid`); `style: "segment"` is `text-style-invalid`.
* Not done: a month has no keyboard arrow-key navigation between days (each day is a button in tab order), no week numbers, no minimum or maximum day; `ticks` is a toggle button (`aria-pressed`), not a `role="radio"`, also for a choice of one; a foot's sticky offset assumes the sheet's 1 rem padding.

### 12.0q Icons: `Icon`, and `icon:` on a `Button` (2026-11-14)

The console's keys, tabs and headings were emoji. An emoji ignores the text colour (so a pressed key, a disabled one and dark mode did not reach it), draws differently on every phone, and cannot be checked at 4.5:1. They are replaced by a line icon set, **Lucide** (ISC licence, with the Feather MIT part), carried by the compiler. The credit line is a licence condition: `THIRD_PARTY.md` names the release tag, the commit and every icon used, the full licence text is `crates/cancho-ui-ir/vendor/lucide/LICENSE`, and **a page that draws an icon carries both notices as a comment in its stylesheet** (`tested`).
* **`Icon { label: ".." name: "bell" size: "small" }`.** `name:` is a string literal of the closed set (the files of `crates/cancho-ui-ir/vendor/lucide/`, listed in `NAMES`); `size:` is `"small"` (1 rem), `"medium"` (1.25 rem, the default) or `"large"` (1.75 rem). `label:` comes first, as on every element.
* **What it is:** an inline `<svg class="cui-icon" data-icon="bell" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round">` whose children are the `path`, `circle`, `rect`, `line` or `polyline` of the vendored file, written verbatim by the compiler. **No `<img>`, no `<use>`, no sprite, no `data:` address, no request**, so a page's Content-Security-Policy is unchanged. It is static: it is in the prerendered HTML as well as drawn by the script. The colour is `currentColor`: it takes the text colour of what holds it, so `pressed:`, a disabled key and dark mode, and the page's 4.5:1 checks on a key's text, apply to it with no rule of its own.
* **Names for a screen reader.** An icon is `aria-hidden` (and `focusable="false"`) when it stands in a `Button` or `NavLink` that has a `label:` (the label is the name) or says `decorative: true` (words beside it say it); otherwise it is `role="img"` with its `label:`. An icon with neither is refused (`icon-label-missing`), as is a blank label, and a label together with `decorative: true` (`icon-label-conflict`).
* **`Button { label: "Pay" icon: "credit-card" on: Pay }`** draws the icon before the label's text: a button with words and an icon. It has a `label:` and no children (`icon-button-invalid`); for a key of only an icon write `Button { label: ".." on: X Icon { name: ".." } }`, which is a key as in 12.0m (an icon, and a second `Text` as its caption).
* **Where it may stand:** anywhere, and as inline content of a `Heading`, `Rich`, `Summary`, `Link`, `Caption` and `Chip` (a chip is text or an icon). A name that is not a literal of the set is refused when the page is built (`icon-unknown`, with the nearest names); a name that is state or built by `+` is a parse refusal, as for any key that must be written in the program.
* **In the script an icon is one call** (`__cui_icon(parent, name, class, px, label | null)`), not the dozen DOM calls it first was: a console with 513 icons carried 1.0 MB of script for them (its gzipped bundle counted, because its server answers a file in one go and cuts off a large one). The shapes are one table, a row for each name the program uses (`const __cui_icon_shapes`), emitted once with the function; the attributes and their order are read back from the recipe (`cancho_ui_ir::icon::svg`), so the call draws the DOM the recipe says and the written page is unchanged. Measured on cancho-ota's console: app.js 7.18 MB to 5.99 MB raw, 444 kB to 367 kB gzipped (that console's `docs/design.md` 30.114).
* **A page with no icon** has no icon rule and no notice: its bytes are what they were. The rules are `cui-icon`, `cui-icon-s`, `cui-icon-l` and `cui-icon-lead`.
* **Adding an icon:** put its name in `crates/cancho-ui-ir/vendor/lucide/NAMES` and run `scripts/vendor_lucide.sh <tag>`: it downloads `icons/<name>.svg` from the official repository at that tag, refuses anything that is not plain (a script, an image, a link, an element outside the five), writes the table and `THIRD_PARTY.md`.
* Tags: `icon-incomplete`, `icon-unknown`, `icon-size-invalid`, `icon-decorative-invalid`, `icon-has-children`, `icon-label-conflict`, `icon-label-missing`, `icon-button-invalid` (`spec/diagnostics/README.md`).
* **Not here:** a name chosen at run time (an `If` of two icons says it), an icon in a `<select>` option or a `Text` (those are text), a second set, a colour of the icon different from its text, animation. Guarantee tier: `tested` for the refusals, the DOM (`tests/icon.rs`, `tests/icon_corpus.json`), the set (every file is plain, both notices kept) and the licence in the page; the look is the console's own browser check (cancho-ota `scripts/icons_check.sh`), and `examples/icons` is the gallery page with every icon of the set.

### 12.0r A picture chosen by the person and a picture drawn from state: `PhotoField` and `Photo`, and a policy on every page (2026-11-16)

The console's four hand-written islands (`avatarpick.js`, `grouphero.js`, `chatmedia.js`, `strip.js` of cancho-ota) each held a copy of the same `shrink()`: decode a chosen file, cut it, draw it again as a JPEG, and try smaller sizes and qualities until its base64 text fits what the server keeps. A hand-written island cannot sit under an `If` or a `For` and is sealed from the network, so each was a place the toolkit's own guarantees stopped (12.0l and the "not built (D)" paragraph of 12.0j said so). Two elements and a baseline policy remove the need for the first three. **Not built here, kept for later phases: the rail/strip of pictures, audio, the recorder** (the fourth island and chat voice notes).

* **`PhotoField { label: "Photo" icon: "camera" square: true max_side: 1024 max_chars: 48000 on: Chosen }`** is a native chooser, modelled on `FileField` (docs/file-upload.md): `<input type=file accept="image/jpeg,image/png,image/webp">`, a user gesture, **no capability**. `label:` and `on:` are required (`photo-field-incomplete`); `icon:` is a name of the Lucide set (12.0q, default `"camera"`; `icon-unknown` otherwise), `square:` `true` (the middle square of the picture) or `false` (the default: the whole picture in its proportions; `photo-square-invalid`), `max_side:` the longest side in pixels (32 to 4096, default 1024) and `max_chars:` the most characters of the base64 text the program is given (100 to 48,000, default 48,000; both `photo-limit-invalid`, integer literals). Not in a `For` (`photo-field-in-loop`: the page keeps its status by the place of the field in the source, as `FileField` does its file); no children (`photo-has-children`).
* **What the page does with the file**, in this order. (1) A file whose type is not `image/jpeg`, `image/png` or `image/webp` is `not a picture`; an empty type is judged by its bytes (some phones give none); `accept` only filters the dialog (`docs/file-upload.md` section 2 measured that it is no guarantee). (2) A file over 40 MiB (41,943,040 bytes) is `too big` and is not read. (3) It is decoded with `createImageBitmap(file, { imageOrientation: "from-image" })`, so **the EXIF orientation is applied**; a browser that refuses the option's value gets the plain call; a file that does not decode is `not a picture`. (4) The middle of it is cut (a square of the shorter side, or the whole picture) and drawn on a canvas **no larger than `max_side:` and never larger than the picture**, on white (a JPEG has no alpha: a transparent PNG would be black). (5) It is encoded as a JPEG at quality 0.82, then, until the **base64 text** (`4 x ceil(bytes / 3)` characters, counted to the character) is at most `max_chars:`: the quality goes down by 0.08 to 0.42, then the side goes down to 0.8 of itself at quality 0.72, to a floor of `max(32, max_side / 4)`; a picture that still does not fit is `too big`. The cap is exact: a text of exactly `max_chars:` is accepted and one more is not.
* **The program is told one JSON `String`**, the way `FileField`'s is: `{"data":"<base64>"}` or `{"error":"too big"}` or `{"error":"not a picture"}`; take it apart with `json.get(r, "data", "")`. Choosing nothing (cancelling the chooser) tells nothing. A choice that a newer one has replaced is told to nobody (a sequence number per field), so a slow large picture cannot arrive after the small one that came later. The input's value is cleared once the file is held, so the same file can be chosen again.
* **Privacy: the text the program gets has no EXIF.** A camera writes the place (GPS), the time, the device and often a thumbnail into the file; **drawing the picture again as a JPEG leaves all of it behind**: the segments of the file before the picture data are the encoder's own, and the page's check (`scripts/check-photo.js`) builds a JPEG with an EXIF block that names a place and finds none of it in what the program is given (no APP1, no comment segment, no marker string). The original file is not kept anywhere by the page. What the program then does with the picture (a server, a log) is the program's; the toolkit cannot say it keeps no more than it is given.
* **Look and accessibility.** The element is a **key** as in 12.0m: an icon (`cui-icon`, 1.25 rem) over the label as its caption, 12 px corners on the `soft` fill, **44 px at least both ways**, the native input laid over the whole key (`opacity: 0`, not `display: none`, so it is the target and takes the keyboard's focus; the key draws a 3 px ring in the accent on `:focus-visible`). **The label is the accessible name** (`aria-label` of the input) and is shown under the icon; a line under the key (`role="status"`, a live region) says what happened: `Preparing the picture`, `Picture added`, `Picture too big`, `Not a picture`. The words are English and not translated by the toolkit (as a key's caption is not, 12.0m); the program has the payload to say its own. The status survives the page's redraws (kept on the component's root by the field's place in the source, like `FileField`'s file).
* **`Photo { label: "The lake" data: picture ratio: "16:9" fit: true tone: colour }`** draws a base64 **JPEG, PNG or WebP** held in state on a canvas. `data:` is a `String` the view reads (a state field, or the name of a `For`: a photo of every row; `photo-data-invalid` for a state field that is not a `String`); `ratio:` a literal `"W:H"` of two whole numbers 1 to 32 (default `"1:1"`; `photo-ratio-invalid`); `fit:` `true` or `false` (the default; `photo-fit-invalid`); `tone:` `"0"` to `"11"` or a `String` the view reads (`photo-tone-invalid`); `decorative: true` **instead of** a `label:` (`photo-label-missing`, `photo-label-conflict`, `photo-decorative-invalid`). It is a `div` of that aspect ratio (`role="img"` and the label, or `aria-hidden`) that the page's script fills with a `canvas` (`aria-hidden`, 720 pixels on its long side, the picture cut to cover it).
* **The formats of a `Photo` (corrected 2026-11-17: the first slice drew JPEG only, and a PNG or a WebP in a chat that an API or a command-line client had filled was a gradient).** A text is a picture when it is base64 (the alphabet, `=` at most twice and only at the end), 100 to 48,000 characters, **and its first twelve bytes (the first sixteen characters) are the signature of one of three formats**: a JPEG (`FF D8 FF`), a PNG (`89 50 4E 47 0D 0A 1A 0A`) or a WebP (`RIFF`, four bytes of size that are not looked at, `WEBP`). The format is told by the bytes and never by a name, a type or a prefix the text says of itself: a `data:` address, a GIF, an SVG, a BMP, an AVIF, a RIFF that is a WAVE, a PNG signature with one byte wrong, are not pictures, and the decoder is not asked. **Why this is no loosening that matters:** the picture is decoded by `createImageBitmap` and drawn on a canvas, the same path the JPEG took; no `<img>`, no `data:` address, no `blob:` URL and no request is made, so **the page's policy is as it was** (`img-src 'self' data:` as before, nothing added), and the size limits are the same (48,000 characters). What the check lets in beyond JPEG is two more of the browser's own raster decoders on a size-bounded text that the page already trusted a decoder with; **SVG stays out** because it can carry script and links, and so do formats a decoder may be newer to (AVIF, GIF, BMP). A text that has the signature and is not a picture (the rest garbage) is refused by the decoder, which leaves the tone gradient. **What did not change:** `PhotoField` always draws the picture again as a JPEG (which takes the EXIF block out), so its handler is only ever given a JPEG, and **replay still refuses a PNG or a WebP as its value** (`trace-value-not-a-photo`); `face(..)`'s photo (12.0l) takes JPEG only, as it did. The check is written in the compiler (`cancho_ui_ir::photo::picture_mime`, `picture_ok`) and in the page (`__cui_photo_kind`, `__cui_photo_ok`), and `tests/photo_corpus.json` is run against both.
* **The proportions of a `Photo` (`fit: true`, corrected 2026-11-17: the box was always the stated `ratio:`, and a portrait picture in a 4:3 box lost its top and bottom).** Without `fit:` nothing changes: the box is the `ratio:` and the picture is cut to cover it. With `fit: true` **the box is the picture's own proportions, width over height, but never narrower than 1:2 nor wider than 2:1**; a picture beyond a bound (a panorama, a long screenshot) is cut to cover the bound, never stretched, and everything else is drawn whole, with no cut and no distortion (the canvas is 720 pixels on its long side, 540 x 720 for a 3:4 picture, the picture drawn at one scale). The `ratio:` is what the box is until the size is known (and for a text that is not a picture). **The box does not change its size when the picture is decoded:** the page reads the size from the header of the text, without decoding it (a PNG's header, a WebP's `VP8X`, `VP8 ` or `VP8L` chunk, a JPEG's frame header, skipping a thumbnail inside an EXIF block), sets the box's ratio in the same turn that the text is set, and turns the two sides round for a JPEG whose EXIF orientation says a quarter turn (5 to 8), which is what the decoder does; so a list of pictures does not move under the reader's thumb. The decoded picture then sets the ratio again; it only differs from the header's when the header could not be read or a PNG or WebP carries an orientation of its own, in which case the box changes once, to the right proportions. *Bounds, and why:* 1:2 is a phone's tallest usual picture (9:16 is 0.56) with room, 2:1 a wide one; a bound keeps one odd picture from making a list of messages a screen high or a hairline. The page's script for the elements is 1.9 KB (about 0.9 KB gzipped) longer (the header reader).
* **Reuse of `face(..)` (12.0l).** The decoder and its cache are `face`'s own (`__cui_face_bmp`: decoded by `createImageBitmap(new Blob(..))`, kept by the text, at most 120, then emptied), so the same picture shown by a person's disc and by a `Photo` is decoded once. The check of the text is the same *rule* but for the format (base64 alphabet with `=` at most twice and only at the end, 100 to 48,000 characters, and a signature of a JPEG, a PNG or a WebP, above), written as `__cui_photo_ok`: **face's own copy is left as it was, JPEG only**, so that a program that draws a `face(..)` and no `Photo` is byte for byte the script it was; `tests/photo_corpus.json` is run against the compiler's `picture_ok` (`tests/photo.rs`), against `__cui_photo_ok` (`scripts/check-photo.js`) and against face's inline check (the limits are read from the page's script). **No `<img>`, no `data:` address, no request, no `innerHTML`, no `blob:` URL**: the page's policy needs nothing for it. A text that is not a picture, or that does not decode, leaves the **tone gradient** (the twelve fixed colours of 12.0l, from the colour to 55 % of it mixed with black; a neutral slate when there is no tone), which is what is shown until the canvas is drawn: so the box is never empty and never a broken image.
* **In a cover card or a banner.** `Column { card: true overlay: "cover" Photo { .. } Text { .. } .. }` and `overlay: "banner"`: a `Photo` is accepted as the first child in place of an `Image`. *The compiler has no rule for what that child is* (`overlay:` is checked as a value only, `overlay-invalid`; the picture is CSS: `:first-child`), so nothing in the compiler changed; three CSS rules did: the photo has square corners in the card, keeps its own tone gradient over the card's dark fill (which the card's `:first-child` rule is more specific than), and in a banner fills the block whatever its ratio (the canvas is cut to cover, `object-fit: cover`) **under a scrim** (black 60 % at the foot, 25 % at the top; a cover card already has one under its second child), because the picture is the person's and no author checked its contrast. That is the group hero of the console with the name over a scrim, with no island.
* **Emitted code only for the pages that use it.** Measured on a page of a button and a counter (`build --page`, `app.js` unminified; bytes): 8,106 plain; **14,474 with a `PhotoField`** (+6.4 KB, 2.1 KB gzipped more; 1.1 KB of it is the camera icon's call and shape table, and a field's page also carries the icon rules and the licence notice, 12.0q); **11,141 with a `Photo`** (+3.0 KB, +0.9 KB gzipped); 17,229 with both (+9.1 KB, +2.7 KB gzipped). A `Photo` in a page that already draws a `face(..)` adds 1.7 KB (the decoder and its cache are shared). The stylesheet of the pictures (`index.html`) is 3.3 KB for a `Photo` alone and 7.3 KB for a field (its icon rules and both licence notices are 4 KB of that). Every other page is the bytes it was: **checked for the 16 gallery demos that existed** (`git diff` of `docs/demo/*/app.js` is empty; their `index.html` gained the one `<meta>` line below), and by `tests/photo.rs` (a program with neither element has no `__cui_photo`, one with `face(..)` and no `Photo` has no photo code).
* **Prerender and replay.** Both elements are holes of the skeleton (a control, and a state-reading box); `inspect prerender` says why. In replay a handler fired only by `PhotoField`s is given only what one can give: `trace-value-not-a-photo` for anything else (exactly one of `data`, base64 starting `/9j/`, at most the longest `max_chars:`, or `error` with one of the two words), as `trace-value-not-a-file` does for a file.

#### The baseline policy: every page has a `Content-Security-Policy`

**Verified before the change** (a program of a button and a text, built with `build --page` and with `build --pwa` from the main branch): no `Content-Security-Policy` in either `index.html`; the policy was written only for a page with a `Map`, a `RouteMap { tiles: .. }` or a sealed island (`img-src`, `frame-src`). So taking the tiles out of the console would have taken its only policy with it. Now `crates/cancho-ui/src/csp.rs` writes, in **every** page of either kind, as the first thing in `<head>`:

`default-src 'self'; script-src 'self' <the SHA-256 of each inline script>; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' <each Network host the program declares>; object-src 'none'; base-uri 'self'`

* **`script-src` lists the inline scripts by hash and has no `unsafe-inline`.** The page has up to four (the sticky header's measure, the app's worker registration, the scroll to a fragment, the motion script); the hashes are computed from the page as it is written, so no inline script an attacker adds is among them (`scripts/check-csp.js` injects one and the browser refuses it). A sealed island's frame is a `srcdoc` document and **inherits the page's policy**, so the SHA-256 of each inline script of its document (read from the island's own `srcdoc`) is added to the page's `script-src` and `frame-src about:` as before (docs/islands.md).
* **`style-src` has `'unsafe-inline'`**, the one inline thing allowed: the page writes `<style>` blocks and `style` attributes (a frame's aspect ratio, a block's maximum width). **`img-src` has `data:`** because the page's own stylesheet draws a faint pattern behind a chat from a `data:` SVG; a map adds its tile hosts to it exactly as before (`'self' data: https://tiles.example`, docs/maps.md). A `Photo`, a `face(..)` and an `Icon` need no entry (a canvas, inline SVG).
* **`connect-src` is `'self'` and each host of `requires Network("host")`**, lower-cased and listed once, written without a scheme (the page's own, with an upgrade from `http` to `https`): the adapter (`net.get`) already refuses any other host before a request is made (docs/adapters.md section 9); now the browser does too. A bare `requires Network;` adds none.
* A program's directive of the same name adds its sources to the baseline's (order kept, no duplicates); any other is added as it is. Nothing is ever removed from the baseline by a program.
* **Measured** (Chromium, `scripts/check-csp.js`): the 17 gallery demos load with no console error, page error or policy violation; a sticky header's inline script ran (`--cui-header-h` set), an app's worker registered and a sealed island's frame ran under the inherited policy; on a page with no map an image from another origin, a request to another origin and an injected inline script are each refused (`securitypolicyviolation` of `img-src`, `connect-src`, `script-src-elem`) while the page's own files are served. Tests: `tests/csp.rs` (the baseline on both builds, first in the head, every inline script by hash, taking a map out leaves the policy, the hosts, the island), `src/csp.rs` (the merge), `scripts/breaks/csp.json` (each rule removed in turn).
* **Not claimed:** a `<meta>` policy cannot carry `frame-ancestors`, `report-uri` or `sandbox`, so the page can still be framed and nothing is reported; a header would, and the server is not this toolkit's. The policy does not bound what an *open* island does (it runs in the page's origin, docs/islands.md section 12). `'unsafe-inline'` for styles is a real loosening: style injection can restyle a page (hide a button, overlay text), though it cannot run script or send data under this policy.

#### Tests and what is not proven

* `tests/photo.rs` and `tests/photo_corpus.json` (refusals with their tags, valid views, picture texts, the script and page of each element and of neither, face with and without photo, replay), `crates/cancho-ui-ir/src/photo.rs` (unit), `tests/look.rs` (the key, the box, the tones, the cover card and the banner, `__cui_photo_draw` run by node against a stand-in document), `tests/csp.rs`, `scripts/check-photo.js` (Chromium, mobile profile, **every picture drawn at test time on a canvas; none is committed**: an oversize picture, an EXIF orientation and place, a PNG with a transparent part, one with no type, text posing as a JPEG, a GIF, an SVG, a file over 40 MiB, a stale choice, a redraw, the exact cap and one under it, a cap nobody can meet, a decorative photo, the demo), `scripts/check-csp.js`, and the mutations `scripts/breaks/photo.json` and `scripts/breaks/csp.json`.
* `scripts/check-photo-formats.js` (Chromium; 2026-11-17; every picture a JPEG, a PNG and a WebP of a portrait, a landscape and a square, drawn and encoded by the browser at run time): every format is drawn; a GIF, an SVG, a WAVE in a RIFF, a cut-short PNG signature, a `data:` address, a text over 48,000 characters and one in lower case are not and the decoder is not asked; `fit: true` boxes and canvases of the picture's own proportions, a red square in the middle stays square, the bounds 1:2 and 2:1 cut and not stretched, the box the same size the moment the text is set and when the picture is drawn (JPEG, PNG, WebP lossy, lossless and with transparency, a JPEG that an EXIF orientation turns), and the page's policy unchanged. `tests/look.rs` reads the header of a PNG, a WebP of each kind and a JPEG with an EXIF thumbnail byte by byte.
* **Not proven:** a real phone (its camera's files: 12-megapixel JPEGs, HEIC, a picture that is a live photo); **HEIC**: Safari on iOS converts a HEIC photo to JPEG for an `accept` list that has no HEIC (it is how the chooser behaves, not tested here), and Chromium on a desktop cannot decode HEIC at all, so a HEIC file under a type of `image/heic` is `not a picture`; Safari and Firefox (`createImageBitmap` with `imageOrientation: "from-image"`, canvas `toBlob` of JPEG, a `<meta>` policy's `script-src` hashes and the inheritance into a `srcdoc` frame were measured in Chromium only); a picture that is a very large PNG (the decode is the browser's, and a 40 MiB file at 100 megapixels can exhaust a phone's memory: the 40 MiB bound is a bound on the file, not on the pixels); the status words in a language other than English; a screen reader (the names and roles are asserted, not heard).
* Guarantee tier: `tested` (the compile-time rules, the text of the script and the CSS, the policy text) and `measured` in Chromium (the behaviour of the chooser and the policy); `trust` for what a browser's JPEG encoder and EXIF handling do beyond the cases above.


### 12.0s A scrolling row that snaps and chooses: `Rail` (2026-11-16)

cancho-ota's console held one more hand-written island, `strip.js`: a row of cards (one for the trip, one for each leg, one for each item) that scrolls sideways, stops each card in the middle, says which card the person tapped or swiped to, and draws dots under it. It was an island because the toolkit had no row that scrolls and no way to choose one of several children: a child cannot tell its parent anything (there are no child-to-parent events), so a card could not say "I was tapped". `Rail` is that row.

* **`Rail { label: "Legs" on: Pick selected: current follow: true snap: "center" gap: 2 item_width: 74 dots: true orientation: "horizontal" .. children }`.** The children are any elements (a `Column { card: true .. }`, a `Photo`, a `For` that makes them); each is one stop of the row. **The scrolling and the snapping are CSS** (`overflow`, `scroll-snap-type: x mandatory`, `scroll-snap-align` on each child): a finger, a wheel and the keyboard scroll it with no script, and a scroll that ends between two children is finished by the browser on the nearest stop.
* **Choosing follows how the toolkit already binds a choice to state** (a `Select` tells `on:` the option, a `Button { on: Pick(n) }` names its row): the **rail** listens (one listener on the row, not one per child) and tells `on:` the **place** of the child, a whole number, 0 for the first; the program keeps it in a state field; **`selected:`** is that field (an `Int` expression the view reads: a state field, a name of a `For`, `cur + 1`; a number out of range or `0 - 1` marks none). The state goes to the view, the event comes back to the state: no new flow. `on:` takes an event of one parameter (or none, if the program does not need the place), as a `Select`'s does; `on: Pick(1)` is `event-args-unsupported`.
* **What a tap is.** A tap, Enter or Space on a child gives `on:` its place. A tap on a `Button`, a link or a field **inside** a child is that control's own and does not choose the child (tested). A child is the direct child of the row as drawn (a `Text` is a child too, as a `span`).
* **Keys.** `label:` (required: a scrolling row is announced by its name; `rail-incomplete`), `on:`, `selected:`, `follow:` (`true` or `false`, default `false`), `snap:` (`"start"` (default), `"center"`, `"end"` or `"none"`), `gap:` (the step 0 to 4 of a `Column`'s, `layout-value-invalid`), `item_width:` (an integer from 20 to 100: the width of a child as a percentage of the row, so that the next one shows at the edge when it is under 100; without it a child is as wide as its content and does not shrink), `dots:` (`true`: a row of small marks under it, one for each child, the chosen one longer; hidden from a screen reader, since the options already say it), `orientation:` (`"horizontal"` (default) or `"vertical"`: a column that scrolls and snaps on y, at most 24 rem high). `selected:` and `follow:` without an `on:` are `rail-selected-needs-on` and `rail-follow-needs-on`; any other key is `binding-unknown`; the six keys above are `binding-unknown` on every other element.
* **`follow: true`: the child that settles in the middle is the chosen one.** After the row has stopped moving for 140 ms the child nearest the place `snap:` puts a child (the middle for `"center"` and `"none"`, the start edge, the end edge) is told to `on:` (if it is not the chosen one), so the child a row stops on is the one it chooses. The scrolling the page itself does (putting the row back, bringing a chosen child into place) is not heard as the person's for 800 ms, so a tap that scrolls the row does not choose every child it passes, and a child that cannot reach the middle (the last of narrow children: the row ends first) stays chosen when it is tapped (measured: no loop, the choice and the position are stable after a swipe, with `snap: "center"` and `"start"`).
* **Roles and keyboard.** With `on:` the row is a `role="listbox"` (`aria-orientation`, `aria-label`) and each child an `option` with `aria-selected`; **one child is in the tab order** (the chosen one, else the first), the arrow keys move the focus and bring the child into view without choosing it (Left and Right on a row, Up and Down on a column, reversed on a right-to-left page for a row), Home and End go to the first and the last, Enter and Space choose. What a child holds that can be focused (a button) is still reached by Tab. Without `on:` the row is a `role="group"` with the label, focusable (`tabindex=0`), so the keyboard can scroll it (the arrow keys are the browser's).
* **The row keeps its place across a render.** The page is drawn again from nothing at every state change, which would put a scrolled row back at its first child. Before the render the position of each rail (found by its place in the source, and its order among those drawn from the same place) is read, and after it put back; a rail whose chosen child **changed** (a tap, a key, the program's own `Next`) brings that child to the place `snap:` says (smoothly, at once for `prefers-reduced-motion`; at once the first time a rail is drawn). A render that did not change the choice leaves the row where the person scrolled it (tested: scrolled by hand away from the chosen child, then an unrelated render: not moved).
* **Look.** The chosen child has a 3 px ring in the accent (`--cui-accent`), the focused one a 3 px outline 3 px outside it; the row has 8 px of padding all round (room for both, which an `overflow` box would cut); the scrollbar is thin and shown. **What a child looks like is the program's** (a card, a `Photo` as the first child of a cover card for a picture behind the text, a tone): the rail adds no colour, no radius and no shadow of its own to its children. The page carries the rules only when a program has a `Rail`; every other page is the bytes it was.
* **Prerender and replay.** A rail is a hole of the skeleton (`inspect prerender` says the page draws it with script). In replay, a handler fired only by `Rail`s is given only a place: `trace-value-not-a-rail-index` for anything that is not a whole number, 0 or more (a `Button` that fires the same event lifts the check, as for the other controls).
* **Policy.** Nothing: no image, no request, no new directive. `scripts/check-csp.js` is unchanged.
* **Replaces** (cancho-ota `ui/assets/strip.js` and `strip.css`): the row of cards that scrolls and snaps to the centre (`Rail { snap: "center" item_width: 74 }`), the selected card's ring and the dots under it (`selected:`, `dots:`), the tap that says which card (`on:`), the swipe that says which card (`follow: true`), the card in the middle at the first draw (the chosen child is brought to its place when a rail is first drawn), Enter and Space on a card. **Not covered by `Rail`, and so by the program or by another element:** the card's look (gradient by kind, price, status pill: `Column { card: true .. }`, `Text`, `Chip`, a `tone`), the card's photo drawn behind its text (`Photo` as the first child of a cover card, 12.0r), and the *Add photo*, *Change* and remove buttons of the selected card (`PhotoField` and a `Button`, in the card, shown only for the chosen one by an `If` on `selected`). The island's pieces of at most 4,000 characters (a frame takes no string longer than 4,096) are not needed: a page's state holds the whole text. One look differs on purpose: a card is not scaled to 96 % and dimmed when it is not chosen (the ring says which is chosen).
* **Tests.** `tests/rail.rs` (every refusal by its tag, the valid views, the script and the page, the keys on other elements, replay, the example, a program cut anywhere), `crates/cancho-ui-ir/src/rail.rs` (unit), `scripts/check-rail.js` (Chromium, mobile profile: roles, the tab stop, the computed snap and size, the first draw, a tap from the protocol's touch events, a tap on a button inside a child, a render that keeps the place, the program choosing, arrows, Home, End, Enter, Space, Tab, a swipe with and without `follow:`, a plain row, a column, the demo), `scripts/breaks/rail.json` (mutations of the script, the compiler's rules, replay, the stylesheet and the hooks of the render).
* **Not proven.** A real phone (a finger on a real screen: the check uses touch events and a scroll gesture the browser synthesizes); Safari and Firefox (scroll-snap with `scroll-padding`, `scrollBy` with `behavior`, `:focus-visible` were measured in Chromium only; iOS has its own momentum, and `scroll-snap-type: mandatory` with `follow:` has not been measured there); a right-to-left page (the arrow keys and the distance are written for it and not measured); a screen reader (the roles and names are asserted, not heard); a row of more than a few hundred children (every render rebuilds them). A very fast fling on a `mandatory` row can skip children on some browsers (`scroll-snap-stop: always` is not set).
* Guarantee tier: `tested` for the refusals, the script and the CSS text; `measured` in Chromium for the behaviour; `trust` for what a browser's scroll-snap does.


### 12.0t A voice note recorded and played from state: `AudioField` and `AudioClip` (2026-11-16)

cancho-ota's other hand-written island, `chatmedia.js`, had four jobs: choose a picture to send (a `PhotoField` does it, 12.0r), draw a picture it was given (`Photo`), play a voice note (a recording decoded by the browser's audio engine, because its frame allowed no `<audio>`), and choose a voice note to send (a file chooser with `capture`, because its frame was not allowed the microphone). The last two are what this section builds: a key that **records**, and a player.

* **`AudioField { label: "Voice note" icon: "mic" max_seconds: 15 max_chars: 48000 on: Recorded }`** is a key (an icon over its caption, 44 px at least, `aria-pressed` while it records) with a time beside it and a status line under it (`role="status"`). `label:` and `on:` are required (`audio-field-incomplete`); `icon:` a name of the Lucide set (12.0q; default `"mic"`; `icon-unknown` otherwise; `mic`, `pause` and `square` were added to the vendored set for this: 118 icons to 121, ISC, `THIRD_PARTY.md`), `max_seconds:` 1 to 60 (default 15) and `max_chars:` 100 to 48,000 (default 48,000), both integer literals (`audio-limit-invalid`). Not in a `For` (`audio-field-in-loop`: the page keeps a recording in progress and its words by the place of the field in the source); no children (`audio-has-children`). Needs no capability: it is a user gesture, and the browser asks the person for the microphone in its own prompt.
* **What a tap does.** The first tap asks for the microphone (status: *Waiting for the microphone*), then records with `MediaRecorder` (status: *Recording, up to 15 seconds*; the key says *Stop* and is pressed; the time runs beside it, hidden from a screen reader: the status is not rewritten every second). It ends at the person's second tap, at `max_seconds:`, or **as soon as the base64 text would reach 90 % of `max_chars:`**; the bit rate is chosen so that `max_seconds:` fits `max_chars:` (three in four characters are bytes, a fifth left for the container; never under 6 kbit/s, never over 128), and a text that is still longer than `max_chars:` is not given: `too big`. **The program is never given a text longer than `max_chars:`** (measured: a cap of 2,500 ended a 10-second recording at about 2.5 s with a text of 2,284 characters; a cap nobody can meet, 100, is `too big` at the first piece).
* **The program is told one JSON `String`**, as a `PhotoField`'s is: `{"data":"<base64>","seconds":7,"mime":"audio/webm"}` (exactly those three keys), or `{"error":"denied"}`, `{"error":"unsupported"}`, `{"error":"no microphone"}`, `{"error":"failed"}` or `{"error":"too big"}`. Take it apart with `json.get(r, "data", "")` (every value is text to `json.get`, `seconds` too). `denied` is the person's no, or the page being in a frame that is not allowed the microphone (the gallery's, for one); `unsupported` is no `MediaRecorder` or no `getUserMedia` (a page that is not on `https` or `localhost` has none); `no microphone`, a device that is not there; `failed`, anything else (including a recording of no bytes). **Each of them is also said in words in the status line** (*The microphone is blocked*, *Recording is not available here*, *No microphone found*, *The recording failed*, *The recording is too long*), and the key is a key again. `mime` is the type of the first bytes (WebM from Chrome, WebM or Ogg from Firefox, MP4 from Safari), **never what the browser says**: the check below is the one the page makes before it gives the text.
* **A recording text**, for the field and the clip: base64 (the alphabet only; `=` at most twice and only at the end), 100 to 48,000 characters, whose first twelve bytes are those of **WebM** (`1A 45 DF A3`), **Ogg** (`OggS`), **MP4** (`ftyp` after four bytes) or **WAV** (`RIFF`, four bytes, `WAVE`). The same closed list and limits as the console's server keeps (cancho-ota docs/design.md 30.42). `cancho_ui_ir::audio::audio_kind` and `__cui_audio_kind` are the compiler's and the page's copies; `tests/audio_corpus.json` (23 cases: the limits one by one, each container, an AVI that is a RIFF, a JPEG, `ftyp` in the wrong place, the padding, url-safe characters) is run against both (`tests/audio.rs`, `scripts/check-audio.js`).
* **`AudioClip { label: "Voice note from Ana" data: clip }`** plays such a text from state: a play key (an icon, 44 px; its accessible name is *Play* or *Pause* and the label), a progress bar (`<progress>`, hidden from a screen reader) and the time (*0:03 / 0:07*). `label:` is required (`audio-clip-label-missing`: a sound nobody names is not a control a screen reader can use), `data:` a `String` the view reads, a state field or a name of a `For` (`audio-clip-incomplete`, `audio-data-invalid`); no children. The text is decoded **when the clip is drawn** (by an `OfflineAudioContext`, which needs no gesture and makes no sound), so the length is on the key before it is tapped; the sound is played by an `AudioContext` made at the first tap. A text that is not a recording is a disabled key with the words *This is not a recording*; an empty one a disabled key with none; one the engine cannot decode says *This recording cannot be played* (a browser that cannot decode WebM, for one).
* **One clip plays at a time**: a tap on another clip stops this one (its key says *Play* again and its bar is back at the start) and starts that one at its beginning. A second tap on the clip that plays pauses it where it is, a third goes on. At the end it stops and is back at its start. **What plays lives outside the elements**, because the page is drawn again at every state change (a poll, a typed letter): the clip that plays is found again by its text, and each render's new key and bar go on with it (measured: a render in the middle left it playing and the bar went on). Two clips with the same text show the same state. Seeking (dragging the bar) is not built.
* **Policy and privacy.** **No change to the policy**: the page has no `<audio>`, no `blob:` or `data:` address and no request for sound, because the engine decodes and plays the text from memory; `media-src` and `blob:` are not in the baseline and are not needed (`tests/audio.rs` asserts the policy of a page with both elements is byte for byte that of a page with neither, and `scripts/check-audio.js` that no `blob:` or `data:` request was made and no violation reported). Nothing is sent anywhere by the page: the text goes to the program's event and no further. The microphone is released (every track stopped) when the recording ends or fails (not measured against the device's recording indicator). `Permissions-Policy` is the server's: a page behind a header that forbids `microphone` gets `denied`.
* **Prerender and replay.** Both are holes of the skeleton. In replay, a handler fired only by `AudioField`s is given only what one can give: `trace-value-not-a-recording` for anything else (exactly `data` of a recording text of at most the longest `max_chars:`, `seconds` from 1 to the longest `max_seconds:` and the `mime` of its first bytes, or exactly one `error` of the five words).
* **Emitted code only for the pages that use it** (the bytes of a page with neither are unchanged: `tests/audio.rs`, and the `app.js` of the 18 earlier demos): the check and the clock for either element, the recorder for a field, the player for a clip; either also carries the icon rules and the licence notice.
* **Replaces** (cancho-ota `ui/assets/chatmedia.js`/`.css`): the voice-note half: **recording a voice note in the browser** (the island could not: its sealed frame was not allowed the microphone, so on a phone the button opened the recorder application's file chooser and elsewhere a file chooser), with a limit in seconds and in characters (the island: a file of at most 36,000 bytes, "about 15 seconds") and words for what went wrong; **playing a voice note** from its base64 text, with play and stop, the time and an accessible name. **The picture half is `PhotoField` and `Photo` (12.0r); no new element is needed for it**: *Picture* is `PhotoField { label: "Picture" icon: "image" max_side: 960 max_chars: 46000 on: Piece }` (the island shrank to 960 px and 46,000 characters: the same keys), drawn with `Photo { data: .. ratio: .. }` (the island drew the picture on a canvas, 168 px high at most; a `Photo` is of a ratio and the full width). **Not covered, and the program's or the app's:** the bubble (a message's picture or voice note inside its place in the chat, the quote, the caption: `Column` and `Row` of the chat styles, 12.0h); what the island's `Piece` event carried: **the pieces of at most 4,000 characters** (a frame took no string longer than 4,096; a page's state holds the whole text, so the page posts it in one request or splits it itself, and the server's `parts` endpoint can stay), the `<kind>|<seconds>|<n>|<last>` record (the field gives `{"data","seconds","mime"}` and a `PhotoField` `{"data"}`: the program adds the kind); the **caption** (a `TextField` of the page); *Only people on the trip can send pictures and voice notes* (an `If` on the program's own flag: the island's `active` and `can_send` props go away, and since these elements can be under an `If` and a `For`, which an island could not, the media area can at last be in the chat sheet and not at the foot of the page); the **file chooser for a recording that is already a file** (`AudioField` records, it does not import: a person with a recording made elsewhere has no way here; a `FileField` gives a file's text but does not check its type); the **duration given by the server** (a clip decodes its own length; a text the engine cannot decode is a disabled key); and the island's guard of 36,000 bytes (the field's cap is in characters, and `max_chars: 48000` is the server's own limit).
* **Tests.** `tests/audio.rs` (every refusal by its tag, the valid views, the corpus, the script and the page, the policy equal to a page without sound, each element alone, a program with neither, replay, the example, a program cut anywhere), `crates/cancho-ui-ir/src/audio.rs` (unit), `scripts/check-audio.js` (Chromium, mobile profile, **Chrome's fake microphone** (`--use-fake-device-for-media-stream`, `--use-fake-ui-for-media-stream`); every sound made at run time, a WAV of a sine; none is committed: the corpus; a tap that records, with the key pressed and the time running; a render during the recording; the end by a tap, by `max_seconds:` and by `max_chars:` (two caps); that the text the program gets is a recording by the compiler's own rule and the player decodes it; the four error words (stubs of `getUserMedia` for denied, none and failed; no `MediaRecorder` for unsupported); the player's play, pause, resume, a render during play, another clip, the end, a text that is not a recording; no media element and no media request; the policy; the demo), `scripts/breaks/audio.json`.
* **Not proven.** A real phone and a real microphone (the fake device plays a beep: the sound is not heard, only that bytes come out and decode); **Safari** (its recorder gives MP4/AAC, which this does not test, and the `webkit` prefixes are written and not run) and **Firefox** (Ogg/Opus and `OfflineAudioContext.decodeAudioData` were not measured); the **permission prompt** (the fake UI flag answers yes: a real prompt, and a person who says no *later* or *never*, are `denied` by the error's name, and that was tested with a stub, not with a person); a recording interrupted by a phone call or by the page going to the background (the recorder's `onerror` and `onstop` are handled; no test does it); the maximum (60 s at the bit rate that fits 48,000 characters, 6.4 kbit/s, which `audioBitsPerSecond` may not honour: the cap on the text is what is guaranteed, not the quality); a screen reader (the names and the live status are asserted, not heard).
* Guarantee tier: `tested` for the refusals, the corpus, the script and CSS text, the policy; `measured` in Chromium (with a fake device) for the recorder and the player; `trust` for what a browser's recorder, decoder and prompt do.
